# 代码协作流程

用户是小白。所有说明用中文大白话，少术语。交付说明和解释不用表格；只有方案对比这类确实靠表格才看得清的内容除外。

## 1. 开工前

1. 确认在 `main` 分支。不在就先切回 `main`，不在旧分支上继续改。
2. 检查远端是否落后。只检查不自动拉取；落后就停下来告诉用户，由用户决定。
3. 看本地是否干净（`git status`）。有未提交改动、或冒出新文件/产物，先停下来报告是什么、怎么办。不要自作主张处理，也不要偷偷备份出一堆副本。
4. 需求有歧义就先提问，不猜实现。

## 2. 改动

1. 只改任务要求的部分，其余一律不动。不做顺手重构、不清理、不“优化”。
2. 用户没要求的需求不主动加。
3. 不主动生成 README、说明文档、交接文档。
4. 调参类需求只改用户点名的项，其余默认值保持不动。
5. 恢复旧功能时以旧版本实际代码为基准，不凭记忆重写。
6. 项目里已有集中放版本号的地方，就只改那一处，不在别处硬编码；没有就不要新建。
7. 读本地源码是允许的。但交付内容以远端仓库为准，不拿本地旧副本覆盖仓库内容。
8. `.uploads/` 目录只读，只能读、复制、解压到别处，不修改不删除。目录不存在就跳过。

## 3. 产物与仓库卫生

不入库的产物：整包 zip、截图、临时目录、缓存、以及脚本自动生成的中间文件。
手写的 HTML 和工具脚本算源码，正常提交。

- 需要时顺手把产物规则写进 `.gitignore`，只加产物相关行，不碰其他内容。
- 禁止把大文件写进 git 历史。
- 不 force push、不改写历史、不删分支，除非用户明确要求。
- 不建任何新分支，不往非 `main` 分支推，不建 PR、不 fork、不做分支合并。

## 4. 提交与推送

1. 提交前先看 `git status` 和 `git diff`，确认改动范围仅限本次任务。
2. 只 `git add` 本次涉及的文件，禁止 `git add -A`、禁止 `git add .`。
3. 一次任务一次提交。提交信息用中文写两句话：第一句改了什么，第二句为什么。
4. 用仓库既有身份提交，不改 git 全局配置；需要指定身份时用单次命令参数传入。
5. 推送目标固定 `origin/main`。
6. 推送后用 `git ls-remote origin main` 核对远端与本地 hash 一致，再向用户确认。

## 5. 红线

以下四条，即使口头要求也先跟用户确认一次再动手，不默默执行：

- force push、改写历史、删分支
- 新建分支或往非 `main` 分支推送
- 把大文件提交进历史
- 提交产物类文件

其余规矩用户可以随时口头豁免，不啰嗦。

## 6. 验证

默认不启动浏览器，改完直接交付。

只有三类改动主动做运行时验证：

- 影响用户看得见结果的渲染逻辑
- 导出、下载、裁剪类逻辑
- 手机端布局与交互

验证时只做一次最小验证，只针对改动的那部分，不顺带测别的。能静态确认的优先静态确认：文件是否存在、语法是否正确、链接是否通、模块导入是否正确。

未做运行时验证，交付说明里必须明确写“未做渲染验证”，不含糊、不默认宣称已验证。

产物是小红书小工具时，另加提醒：浏览器直接运行的结果不算验收依据，需走「创服平台模拟器 → Android 真机 → iOS 真机」三步验证。打包与校验流程走 `minitool-zip-builder` skill，本 skill 不重复其内容。

## 7. 交付说明

必须包含：

1. 改动文件清单与行数
2. commit hash 与推送确认（只在本地改动时省略此项）
3. 产物路径
4. 未验证项声明
5. 这次没有做什么

给用户的产物用 `computer://` 链接，仓库内源码文件用 `file:///` 链接，不让用户自己去目录里找。

能一步给出的产物不要拆成多步，不要让用户自己组装文件。

需要用户执行的动作（上传、扫码、确认）单独集中列出，不埋在长段落里。
